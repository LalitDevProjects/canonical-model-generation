Introduction This specification is written to be built from. It defines the components, data contracts, algorithms, agent specifications, interfaces and tests of the canonical model generation platform in enough detail that an engineering team can implement it without returning for further design decisions. 1.1 Purpose and audience The primary audience is the engineering team that will build the platform, and the architects and reviewers who must assure it. Secondary audiences are the data architect, who owns the contracts in ??3, and the QA lead, who owns ??16. Business stakeholders are not the audience for this document. It is deliberately self-contained. Where context from the solution design is needed to make a technical decision intelligible, that context is restated here rather than cross-referenced, so this document can circulate to an implementation partner on its own. 1.2 What the system does The syndicate operates Retail insurance across three regions ??? US, UK and EU ??? each with its own core systems and its own externally facing API contracts. External counterparties therefore integrate three times, once per region. The intended remedy is a single canonical model per business domain that all three regions can be mapped onto, so that the external boundary can eventually expose one contract instead of three. This platform derives those canonical models. It reads the syndicate???s existing evidence ??? source repositories, interface definitions, knowledge bases, API catalogues and vendor models ??? normalises everything into one intermediate representation, clusters attributes across regions by meaning, aligns the result to the ACORD Reference Architecture, proposes a canonical model, measures how much of the regional estate that model covers, and emits the artefacts a human ratification workshop needs in order to acc ept or amend it. It produces five artefacts per domain release: canonical contracts as  OpenAPI  3.1 with shared JSON Schema components; bidirectional region-to-canonical mapping specifications with generated round-trip tests; a tool-neutral logical model with glossary and lineage; coverage and gap reports; and a signed release manifest.  The platform proposes. Humans ratify.  No artefact reaches a release without a named human approver, and that constraint shapes the whole design ??? most visibly in the checkpoint states in ??8.1 and the evidence invariants in ??3.2. Wave 1 is the  Claims  domain: the claim core plus the shared Party, Address, Money, Document, Contact and Identifier sub-models that every later domain will reuse. 1.3 Scope and non-goals In scope Explicit non-goals Every component in ??2.1, its interfaces and its internal algorithms The external interface layer: gateway, routing, orchestration, fan-out All internal data contracts, specified as JSON Schema (??3) Consumer authentication, authorisation and consent Agent prompt templates, tool contracts and guardrail enforcement (??7) Runtime latency, throughput and availability engineering Core algorithms with executable Python (??9) Asynchronous or event canonical contracts ??? events are evidence only The mapping DSL grammar, transform library and interpreter (??10) Migration or decommissioning of existing point-to-point integrations Internal service APIs (??12), security (??13), observability (??14) Selection or replacement of any regional core platform Test strategy including the agent evaluation harness (??16) Production support model beyond the runbook in ??18 The proof-of-concept build sequence with acceptance tests (??17) Commercial tooling evaluation 1.4 Conventions Convention Meaning MUST / MUST NOT An absolute requirement. A  run  processes one domain against one corpus. Runs are triggered on demand or by the re-baseline schedule; there is no request path and nothing in this system is latency-sensitive. Concurrency exists to shorten elapsed time, not to serve load. Within a run, the orchestrator fans out over  work items  ??? a repository, a specification document, a concept cluster ??? and each item flows through its stage chain independently. Barriers are used only where a stage genuinely needs the complete prior set:  S4  clustering,  S7  scoring and partitioning, and  S8  emission. Everywhere else pipelining is used, so a slow artefact does not hold up the rest. Agent invocations are stateless. Everything an agent needs arrives in its prompt and through  substrate- api ; everything it produces is written back through  tool-gateway . An agent MUST NOT hold state between invocations, because a retried invocation must be indistinguishable from a first one. 2.5 Cross-cutting rules Contracts first.  No component may define its own data shapes. Every inter-component payload is one of the contracts in ??3, validated at both ends. Content addressing.  Artefacts and chunks are keyed by SHA-256 of their content. Re-ingesting identical content MUST be a no-op, which is what makes re-baseline cheap. Idempotency.  Every stage MUST be safe to re-run on the same input with the same run identifier. Deterministic stages MUST produce byte-identical output. No ambient credentials.  Components obtain short-lived credentials from the workload identity provider per invocation. Static tokens in configuration are a build failure. Fail loud.  A stage that cannot meet its exit criterion halts that work item and raises a finding. Silent degradation is prohibited, because the resulting coverage number would be dishonest. Everything is journalled.  Every stage transition, agent invocation, tool call and human decision emits a journal event (??3.10). 3.
